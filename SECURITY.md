# Security / 安全报告

## Report privately / 私密报告

After the repository is published and private vulnerability reporting is enabled, open the repository's **Security → Advisories → Report a vulnerability** page. Include a concise description, impact, and a fictional or redacted reproduction. Never attach working credentials, real transcripts, recordings, account exports, or private source. Do not put the report in a public Issue, Discussion, or PR.

仓库公开并启用私密漏洞报告后，通过 **Security → Advisories → Report a vulnerability** 提交简要描述、影响和虚构或脱敏的复现。不要附带可用凭据、真实转写、录音、账号导出或私有源码，也不要放到公开 Issue、Discussion 或 PR。

If that entry is unavailable, keep sensitive details private. Do not substitute a public Issue. This repository must not be launched until the reporting route is verified. No response-time or bounty commitment is made here.

如果没有该入口，保留敏感细节，不要改用公开 Issue。私密报告方式验证通过前不得发布仓库。本文不承诺响应时间或漏洞奖励。

## Respond to a disclosure / 泄露处置

1. Revoke or rotate affected credentials immediately. Stop relevant automation and contain further disclosure. Share sensitive evidence only with authorized responders.
2. Identify affected data, destinations, permissions, and exposure times. Preserve minimal evidence privately and assess notification obligations through the appropriate internal process.
3. Remove exposed material and request cleanup of cached or downstream copies where possible. Deleting a file, rewriting history, or making a repository private does not undo exposure.
4. Re-run content, history, and permission reviews before restoring affected automation or publishing follow-up material. Publish only a reviewed, non-sensitive summary when appropriate.

1. 立即撤销或轮换受影响凭据，停止相关自动化、控制继续披露；敏感证据只交给有权限的处理人员。
2. 核实涉及的数据、去向、权限和暴露时间；私下保留最少必要证据，通过适当内部流程评估通知要求。
3. 移除暴露材料，并尽可能请求清理缓存和下游副本。删文件、重写历史或改回私有都不能撤销已经发生的披露。
4. 恢复相关自动化或发布后续材料前，重新检查内容、历史和权限。适当时只公开经审查、不含敏感信息的说明。
